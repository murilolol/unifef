Introdução

Por que utilizar Views?

Em sistemas reais, consultas podem envolver muitos JOINs, filtros, cálculos e regras de negócio. Repetir a mesma lógica em vários lugares torna o código difícil de manter.

Simplificar

Ocultar a complexidade de consultas extensas.

Reutilizar

Centralizar uma consulta usada por vários relatórios ou aplicações.

Controlar

Expor apenas as colunas e linhas que determinado usuário pode acessar.

Conceito

O que é uma View?

Uma view é uma consulta SQL armazenada no banco de dados e apresentada ao usuário como se fosse uma tabela.

CREATE VIEW vw_produtos_caros AS
SELECT id_produto, nome_produto, preco
FROM produtos
WHERE preco > 1000;
Importante: uma view comum não armazena uma cópia independente dos dados. Quando é consultada, o PostgreSQL utiliza a definição da view para buscar os dados nas tabelas de origem.

Sintaxe

Criando a primeira View

CREATE VIEW nome_da_view AS
SELECT colunas
FROM tabela
WHERE condicao;

Exemplo:

CREATE VIEW vw_clientes_sp AS
SELECT id_cliente, nome, cidade
FROM clientes
WHERE estado = 'SP';
Após criada, vw_clientes_sp passa a ser um objeto do banco que pode ser utilizado em consultas.
Consulta

Consultando uma View

O acesso é feito da mesma forma que em uma tabela:

SELECT *
FROM vw_clientes_sp;

Também é possível filtrar novamente:

SELECT nome, cidade
FROM vw_clientes_sp
WHERE cidade = 'Campinas';
O filtro da consulta externa é aplicado sobre o conjunto de dados definido pela view.
Funcionamento

O que acontece quando a View é consultada?

1

Aplicação consulta a view

SELECT * FROM vw_clientes_sp;

2

PostgreSQL utiliza a definição

A consulta armazenada da view é integrada ao plano de execução.

3

As tabelas reais são acessadas

Os dados atuais são lidos das tabelas de origem.

Se os dados das tabelas mudarem, a view comum passa a apresentar os novos valores automaticamente.
Reutilização

Sem View × Com View

Sem view

SELECT p.id_pedido,
       c.nome,
       p.data_pedido
FROM pedidos p
JOIN clientes c
  ON p.id_cliente = c.id_cliente;

Com view

SELECT *
FROM vw_pedidos_clientes;

A complexidade fica concentrada na definição da view, enquanto as consultas posteriores tornam-se menores e mais legíveis.

JOIN

View com relacionamento entre tabelas

CREATE VIEW vw_pedidos_clientes AS
SELECT
  p.id_pedido,
  p.data_pedido,
  p.status,
  c.id_cliente,
  c.nome AS cliente
FROM pedidos p
JOIN clientes c
  ON p.id_cliente = c.id_cliente;
Benefício: quem consulta a view não precisa conhecer o relacionamento entre pedidos e clientes.
JOIN múltiplo

View detalhada de vendas

CREATE VIEW vw_detalhes_vendas AS
SELECT
  p.id_pedido,
  c.nome AS cliente,
  pr.nome_produto,
  ip.quantidade,
  ip.preco_unitario,
  ip.quantidade * ip.preco_unitario AS subtotal
FROM pedidos p
JOIN clientes c
  ON p.id_cliente = c.id_cliente
JOIN itens_pedido ip
  ON p.id_pedido = ip.id_pedido
JOIN produtos pr
  ON ip.id_produto = pr.id_produto;
Uso prático

Consultando a View detalhada

SELECT
  id_pedido,
  cliente,
  nome_produto,
  subtotal
FROM vw_detalhes_vendas
WHERE subtotal > 1000
ORDER BY subtotal DESC;

Para relatórios

A aplicação acessa um conjunto de dados já organizado.

Para manutenção

Alterações na lógica podem ser centralizadas na própria view.

Agregação

View com GROUP BY e SUM

CREATE VIEW vw_total_pedidos AS
SELECT
  p.id_pedido,
  c.nome AS cliente,
  SUM(ip.quantidade * ip.preco_unitario)
    AS valor_total
FROM pedidos p
JOIN clientes c
  ON p.id_cliente = c.id_cliente
JOIN itens_pedido ip
  ON p.id_pedido = ip.id_pedido
GROUP BY p.id_pedido, c.nome;
Views com agregação são excelentes para relatórios, mas normalmente não são atualizáveis diretamente.
Agregação

View de resumo por cliente

CREATE VIEW vw_resumo_clientes AS
SELECT
  c.id_cliente,
  c.nome,
  COUNT(p.id_pedido) AS quantidade_pedidos
FROM clientes c
LEFT JOIN pedidos p
  ON c.id_cliente = p.id_cliente
GROUP BY c.id_cliente, c.nome;

Consulta posterior:

SELECT *
FROM vw_resumo_clientes
WHERE quantidade_pedidos >= 2;
Alteração

CREATE OR REPLACE VIEW

Quando é necessário modificar a consulta de uma view, o PostgreSQL permite substituir sua definição.

CREATE OR REPLACE VIEW vw_clientes_sp AS
SELECT
  id_cliente,
  nome,
  cidade,
  limite_credito
FROM clientes
WHERE estado = 'SP';
Atenção: existem restrições na substituição. As colunas existentes precisam continuar compatíveis; mudanças estruturais maiores podem exigir remover e recriar a view.
Nomes de colunas

Definindo aliases claros

CREATE VIEW vw_produtos_categoria AS
SELECT
  p.id_produto,
  p.nome_produto AS produto,
  c.nome_categoria AS categoria,
  p.preco
FROM produtos p
JOIN categorias c
  ON p.id_categoria = c.id_categoria;
Uma view funciona como uma interface de dados. Por isso, nomes de colunas claros tornam seu uso mais intuitivo para outros desenvolvedores.
Organização

Convenções de nomenclatura

Prefixo

Uma convenção comum é utilizar vw_:

vw_clientes_sp
vw_total_pedidos

Nome descritivo

O nome deve indicar claramente o que a view representa, evitando abreviações difíceis de interpretar.

Não é obrigação do PostgreSQL usar vw_, mas uma convenção consistente facilita manutenção e leitura do esquema.
Exclusão

DROP VIEW

DROP VIEW vw_clientes_sp;

Para evitar erro caso a view não exista:

DROP VIEW IF EXISTS vw_clientes_sp;
Cuidado: outras views ou objetos podem depender dela. Nesses casos, o PostgreSQL pode impedir a remoção.
Dependências

CASCADE e RESTRICT

DROP VIEW vw_base RESTRICT;

RESTRICT impede a exclusão caso existam objetos dependentes.

DROP VIEW vw_base CASCADE;

CASCADE remove também objetos dependentes.

Utilize CASCADE com muito cuidado, especialmente em bancos compartilhados ou de produção.
Atualização

Uma View pode receber INSERT, UPDATE e DELETE?

Algumas views simples podem ser automaticamente atualizáveis no PostgreSQL.

CREATE VIEW vw_clientes_sp AS
SELECT id_cliente, nome, cidade, estado
FROM clientes
WHERE estado = 'SP';
UPDATE vw_clientes_sp
SET cidade = 'Jundiaí'
WHERE id_cliente = 2;
Se a view for atualizável, a modificação é aplicada na tabela base clientes.
Limitações

Quando uma View deixa de ser simples?

Views que utilizam determinadas construções normalmente não são automaticamente atualizáveis.

Exemplos comuns

  • GROUP BY
  • funções de agregação
  • DISTINCT
  • operações de conjunto

Por quê?

O PostgreSQL pode não conseguir determinar de maneira inequívoca qual linha da tabela original deve ser modificada.

Integridade

Problema ao atualizar uma View filtrada

Considere a view:

CREATE VIEW vw_clientes_sp AS
SELECT *
FROM clientes
WHERE estado = 'SP';

Sem proteção adicional, uma alteração pode fazer a linha deixar de satisfazer o filtro:

UPDATE vw_clientes_sp
SET estado = 'MG'
WHERE id_cliente = 1;
Após a alteração, o cliente continua na tabela, mas deixa de aparecer na view.
Integridade

WITH CHECK OPTION

CREATE VIEW vw_clientes_sp AS
SELECT id_cliente, nome, cidade, estado
FROM clientes
WHERE estado = 'SP'
WITH CHECK OPTION;

Agora, operações feitas através da view precisam gerar linhas que continuem atendendo ao filtro.

UPDATE vw_clientes_sp
SET estado = 'MG'
WHERE id_cliente = 1;
-- operação rejeitada
Segurança

View como camada de acesso

Uma view pode expor somente determinadas colunas de uma tabela.

CREATE VIEW vw_clientes_publico AS
SELECT
  id_cliente,
  nome,
  cidade,
  estado
FROM clientes;

Expostos

Nome, cidade e estado.

Ocultos

Campos internos, financeiros ou outros dados que não precisam ser entregues ao usuário.

Permissões

GRANT em uma View

GRANT SELECT
ON vw_clientes_publico
TO usuario_relatorios;

Com uma política de permissões adequada, é possível dar acesso à view sem permitir que o usuário consulte diretamente todas as tabelas envolvidas.

Segurança em banco exige planejamento de privilégios, proprietário dos objetos e contexto de execução. A view é uma ferramenta dessa estratégia, não uma solução isolada.
Boas práticas

Views não substituem o projeto do banco

Não esconder problemas

Uma view não corrige modelagem inadequada ou ausência de índices.

Evitar excesso

Muitas camadas de views sobre views podem dificultar entendimento e manutenção.

Documentar

Views importantes devem possuir finalidade e dependências bem conhecidas.

Desempenho

View comum melhora a velocidade?

Não necessariamente. Uma view comum é principalmente uma forma de organizar e reutilizar uma consulta.

O otimizador do PostgreSQL normalmente integra a definição da view à consulta e gera um plano de execução sobre as tabelas reais.

Se a consulta original é pesada, criar uma view comum sobre ela não significa que o resultado será armazenado ou ficará automaticamente mais rápido.

Análise

EXPLAIN ANALYZE em uma View

EXPLAIN ANALYZE
SELECT *
FROM vw_total_pedidos
WHERE valor_total > 3000;

O plano permite observar quais tabelas são acessadas, como os JOINs são executados e onde estão os maiores custos.

Uma view pode simplificar o SQL escrito pelo usuário sem esconder o plano real do PostgreSQL.
Materialized View

Quando o resultado precisa ser armazenado

Uma materialized view armazena fisicamente o resultado da consulta.

CREATE MATERIALIZED VIEW mv_vendas_por_cliente AS
SELECT
  c.id_cliente,
  c.nome,
  SUM(ip.quantidade * ip.preco_unitario) AS total
FROM clientes c
JOIN pedidos p
  ON c.id_cliente = p.id_cliente
JOIN itens_pedido ip
  ON p.id_pedido = ip.id_pedido
GROUP BY c.id_cliente, c.nome;
Comparação

View × Materialized View

CaracterísticaViewMaterialized View

Atualização

REFRESH MATERIALIZED VIEW

REFRESH MATERIALIZED VIEW
mv_vendas_por_cliente;

Depois do REFRESH, o conteúdo armazenado é recalculado a partir das tabelas base.

Uma materialized view pode apresentar dados desatualizados entre dois processos de atualização.
Índices

Índices em Materialized Views

Como a materialized view armazena dados fisicamente, ela pode possuir índices próprios.

CREATE INDEX idx_mv_vendas_cliente
ON mv_vendas_por_cliente(id_cliente);
Esse recurso é útil em relatórios pesados ou consultas analíticas executadas repetidamente sobre dados que não precisam ser atualizados a cada instante.
Erros comuns

SELECT * dentro de Views

CREATE VIEW vw_clientes AS
SELECT *
FROM clientes;

Apesar de funcionar, pode tornar a interface da view menos explícita e mais sensível a mudanças de estrutura.

CREATE VIEW vw_clientes AS
SELECT id_cliente, nome, cidade, estado
FROM clientes;
Prefira declarar conscientemente quais colunas fazem parte da view.
Erros comuns

Views excessivamente complexas

Problema

Uma view chama outra, que chama outra, que possui vários JOINs e agregações.

Consequência

O SQL externo parece simples, mas a consulta real pode ser difícil de compreender e otimizar.

Views devem reduzir complexidade para o consumidor sem criar uma estrutura de dependências impossível de manter.
Aplicação

Quando uma View é uma boa escolha?

Relatórios recorrentes

Quando várias telas precisam da mesma combinação de tabelas.

Compatibilidade

Quando se deseja oferecer uma interface estável mesmo com mudanças internas controladas.

Segurança

Quando usuários devem visualizar apenas subconjuntos de dados.

Padronização

Quando cálculos e regras de consulta devem ser centralizados.

Exemplo integrado

Relatório de vendas pronto para uso

CREATE VIEW vw_relatorio_vendas AS
SELECT
  p.id_pedido,
  p.data_pedido,
  p.status,
  c.nome AS cliente,
  SUM(ip.quantidade * ip.preco_unitario) AS total
FROM pedidos p
JOIN clientes c
  ON p.id_cliente = c.id_cliente
JOIN itens_pedido ip
  ON p.id_pedido = ip.id_pedido
GROUP BY
  p.id_pedido, p.data_pedido, p.status, c.nome;
Exemplo integrado

Consultas sobre o relatório

SELECT *
FROM vw_relatorio_vendas
WHERE status = 'Pago'
ORDER BY total DESC;
SELECT cliente, SUM(total) AS total_cliente
FROM vw_relatorio_vendas
GROUP BY cliente
ORDER BY total_cliente DESC;
A view pode servir como uma nova camada lógica sobre a qual outras consultas são construídas.
